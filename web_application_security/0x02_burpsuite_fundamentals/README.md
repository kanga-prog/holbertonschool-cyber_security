# Burp Suite Fundamentals – Web Application Security (0x02)

## Overview

This repository documents the practical exploitation steps and security lessons learned while completing the **Burp Suite Fundamentals** web application security challenges from the Holberton School curriculum.

The objective of these tasks is to understand how weak session management and insecure token handling can lead to **session hijacking** and **privilege escalation**.

The work focuses mainly on:

* Analyzing session cookies with **Burp Sequencer**
* Manipulating cookies and headers using **Burp Proxy**
* Decoding, modifying, and re-encoding tokens with **Burp Decoder**

## Task 5 – Session Hijacking & Token Predictability

### Goal

Identify and exploit weak session handling by analyzing the `hijack_session` token generated by the application.

---

### Observation

While interacting with `/task5/`, the server issues two cookies:

* `session` – main authentication session
* `hijack_session` – secondary session identifier

Example:

```
hijack_session=04467efe-d1aa-424f-9b52-910506d7ac1e-176970001505
```

---

### Analysis with Burp Sequencer

Using **Burp Sequencer**, multiple `hijack_session` values were captured and analyzed.

Findings:

* The token is composed of two parts:

  * A static UUID-like value
  * A timestamp-like incremental suffix
* Tokens are **highly predictable**
* Very low entropy
* Sequential generation

This indicates a **critical session management vulnerability**.

---

### Exploitation

To bypass the hijacking protection:

* The `hijack_session` cookie was removed or set to an empty value in the request header

Example request:

```
Cookie: session=<valid_session>; hijack_session=
```

The server failed to properly validate the absence of the `hijack_session` token and allowed access.

---

### Result

The application responded with a success message and revealed the flag:

```
FLAG: 8be1831b6f3c5e573d4ee52f649a78db
```

---

### Security Impact

* Session hijacking is possible
* Token prediction enables replay attacks
* Missing server-side validation

## Task 6 – Bearer Token Manipulation (Decoder)

### Goal

Escalate privileges by decoding and modifying a **Base64 + GZIP encoded Bearer Token**.

---

### Intercepting the Request

* Navigated to `/task6/`
* Intercepted a request containing an `Authorization` header:

```
Authorization: Bearer <token>
```

---

### Decoding the Token

Using **Burp Decoder**, the token was processed as follows:

1. Base64 Decode
2. GZIP Decompression

Resulting payload:

```json
{
  "username": "kanga-prog",
  "admin": false
}
```

---

### Token Manipulation

The JSON was modified to escalate privileges:

```json
{
  "username": "kanga-prog",
  "admin": true
}
```

Then:

1. GZIP Compression
2. Base64 Encoding

---

### Exploitation

* The modified token replaced the original Bearer token in the `Authorization` header
* The request was forwarded

---

### Result

The server trusted the client-side token without integrity validation and granted elevated privileges, revealing the hidden flag.

The flag was successfully extracted and saved to:

```
6-flag.txt
```

---

## Key Vulnerabilities Identified

### 1. Predictable Session Tokens

* Low entropy
* Timestamp-based generation
* Vulnerable to replay and hijacking

### 2. Insecure Token Trust Model

* No signature (HMAC / JWT signature missing)
* No server-side verification
* Client-controlled privilege escalation

---

## Security Lessons Learned

* Session tokens must be:

  * Cryptographically random
  * Non-predictable
  * Properly validated server-side

* Authorization tokens must:

  * Be signed (JWT with HMAC/RSA)
  * Never trust client-modifiable fields
  * Enforce server-side privilege checks

---

## Conclusion

These tasks demonstrate how **small implementation mistakes** in session and token handling can lead to **complete authentication and authorization bypasses**.

Burp Suite proves to be a powerful tool not only for exploitation, but for **understanding why secure design matters**.
